# Поток данных: Market Data — Caching & Real-Time Push

## Обзор архитектуры

Система построена на гибридной модели взаимодействия: REST API выступает детерминированным источником данных и механизмом fallback, WebSocket служит транспортным слоем для событийной синхронизации, Redis выполняет роль распределённого кэша с жёстким контролем свежести. React Query оркестрирует состояние на клиенте, бизнес-логика строго инкапсулирована в `MarketService`, шлюз `MarketGateway` отвечает исключительно за маршрутизацию событий и не содержит правил резолвинга или кэширования. Контракт данных минималистичен: фронтенд получает только массив цен, вся логика кэширования инкапсулирована на бэкенде.

## Часть 1: REST API и Redis Caching

### Архитектура запроса

Система построена по принципу слоистого кэширования с обратной связью. Фронтенд запрашивает цены через React Query, бэкенд маршрутизирует запрос через четыре уровня хранения, а Redis выступает основным распределённым слоем.

### Этап 1: Инициация на фронтенде

Хук `useMarketData` формирует детерминированный `queryKey` на основе отсортированного массива символов. React Query проверяет внутреннее состояние: если данные отсутствуют или помечены как устаревшие (`staleTime: 60_000`), отправляется GET-запрос к `/market`. Параметр `staleTime` ограничивает частоту сетевых вызовов до 1 раза в минуту.

### Этап 2: Резолвинг и проверка Redis

Бэкенд получает массив символов и передаёт его в `CoinResolverService`. Сервис проходит по каскаду: **память процесса → Redis → PostgreSQL → внешний API**. После получения CoinGecko IDs бэкенд сортирует их и формирует уникальный ключ кэша в формате `market:bitcoin,ethereum`. Далее выполняется проверка Redis на наличие готовых рыночных данных.

### Этап 3: Обработка кэш-промаха и защита от Stampede

Если ключ отсутствует, срабатывает механизм защиты от параллельных промахов. Бэкенд пытается захватить распределённый лок через атомарную команду `SET key value EX ttl NX` с TTL 5 секунд. Если лок уже занят другим воркером, текущий поток переходит в режим ожидания 200 миллисекунд и повторно проверяет Redis. Это предотвращает синхронный наплыв 100 тысяч запросов на внешний API при истечении TTL.

### Этап 4: Внешний запрос и запись в кэш

Владелец лока выполняет единственный запрос к CoinGecko `/coins/markets`. Ответ нормализуется, приводится к внутреннему DTO и записывается в Redis с TTL ровно 300 секунд.

### Этап 5: Возврат данных

Фронтенд получает массив `MarketData[]`. React Query кэширует ответ в памяти браузера. При следующем взаимодействии пользователя или фокусе окна React Query проверяет `staleTime`, отправляет запрос, а бэкенд возвращает данные из Redis до истечения TTL. Цикл замыкается.

### Итог (REST-часть)

Данные движутся по модели запрос-ответ: **браузер → бэкенд → Redis → внешний API → Redis → браузер**. При высоких нагрузках Redis абсорбирует ~99% запросов. Механизм локов гарантирует, что при истечении пяти минут обновлением займётся ровно один воркер, остальные получат готовые данные без нагрузки на инфраструктуру.

## Часть 2: WebSocket Push и Реактивная Синхронизация

### Архитектура взаимодействия

WebSocket расширяет REST-модель событийной синхронизацией в реальном времени. Транспорт и бизнес-логика строго разделены: `MarketService` не знает о сокетах, `MarketGateway` не знает о монетах.

### Этап 1: Инициация канала

При монтировании корневого компонента фронтенд вызывает `useMarketSocket`. Клиент открывает постоянное TCP-соединение с пространством имён `/market`. Socket.IO выполняет handshake, фиксирует транспорт `websocket` и начинает отправлять heartbeat-пакеты. Бэкенд регистрирует подключение в `MarketGateway.handleConnection`. Канал готов к двунаправленной передаче событий.

### Этап 2: Первичная загрузка (REST)

React Query формирует `queryKey` и отправляет `GET /market?symbols=...`. `MarketController` делегирует вызов в `MarketService`. Сервис проходит каскад `CoinResolverService`: память процесса → Redis → PostgreSQL → CoinGecko Search. После получения ID формируется детерминированный ключ `market:ids`. При кэш-промахе выполняется внешний запрос к `/coins/markets`, ответ нормализуется в `MarketData[]` и записывается в Redis с TTL 300 секунд. Данные возвращаются клиенту, React Query сохраняет их в памяти браузера.

### Этап 3: Триггер обновления и Push

Сразу после успешной записи в Redis `MarketService` вычисляет абсолютную метку истечения: `expiresAt = Date.now() + CACHE_TTL * 1000`. Вызывается `this.gateway.broadcastCacheUpdate(expiresAt)`. Шлюз выполняет `server.emit('market:sync', { type: 'cache_updated', expiresAt })`. Событие мгновенно доставляется всем активным клиентам в namespace `/market`.

### Этап 4: Реакция фронтенда и инвалидация

Хук `useMarketSocket` перехватывает `market:sync`. При `type === 'cache_updated'` вызывается `queryClient.invalidateQueries({ queryKey: ['market'] })`. React Query помечает текущий кэш как `stale` и в фоне инициирует тихий `GET /market`. Бэкенд мгновенно отвечает из Redis (1–2 мс), так как данные были только что обновлены. UI перерендеривается без скачков, дублирования нагрузки на CoinGecko или нарушения контракта DTO.

### Этап 5: Синхронизация TTL и прогресс-бар

Поле `expiresAt` из WS-события передаётся в компонент индикатора. Клиент вычисляет остаток: `remaining = expiresAt - Date.now()`. На основе значения рендерится прогресс-бар, визуализирующий время до следующего планового обновления кэша. При получении нового `market:sync` таймер сбрасывается. Механизм опирается на серверную метку, что исключает рассинхронизацию при throttling браузера, уходе вкладки в фон или кратковременной потере сети.

### Этап 6: Отказоустойчивость и Graceful Degradation

При обрыве соединения Socket.IO автоматически пытается восстановить канал (до 5 попыток с экспоненциальной задержкой). Если реконнект исчерпан, фронтенд прозрачно переключается на polling через React Query (`staleTime: 60_000`). Пользователь продолжает получать данные с задержкой не более 1 минуты. При восстановлении WS-канала события начинают поступать снова, цикл замыкается без вмешательства пользователя и потери состояния.

### Итог (WebSocket-часть)

Данные движутся по гибридной модели: REST гарантирует валидацию контрактов и детерминированность, WebSocket обеспечивает реактивность и мгновенную синхронизацию. `MarketService` остаётся единственной точкой входа для бизнес-логики, `MarketGateway` выступает тонким транспортным адаптером. Redis абсорбирует ~99% запросов, инвалидация через WS исключает лишние сетевые вызовы.

## Финальный итог

Система реализует замкнутый цикл данных с двумя контурами:

1. **REST-контур** — детерминированная загрузка и валидация контрактов, кэширование в Redis, защита от stampede через распределённые локи.
2. **WebSocket-контур** — реактивная синхронизация, мгновенная инвалидация кэша, визуализация TTL, graceful degradation при потере соединения.

Архитектура готова к горизонтальному масштабированию: добавление графиков, исторических срезов или price-alerts потребует лишь регистрации новых событий в шлюзе без модификации ядра системы или нарушения текущего REST-флоу.

### Ключевые компоненты

| Компонент | Роль |
|---|---|
| **React Query** | Клиентское кэширование, инвалидация, polling fallback |
| **MarketGateway** | Транспортный адаптер WebSocket, маршрутизация событий |
| **MarketService** | Единственная точка бизнес-логики, оркестрация кэша |
| **CoinResolverService** | Каскадный резолвинг ID (память → Redis → PostgreSQL → API) |
| **Redis** | Распределённый кэш (TTL 300с), распределённые локи (TTL 5с) |
| **Socket.IO** | Дуплексный канал, heartbeat, автореконнект |

### Временные характеристики

- `staleTime` (React Query): 60 секунд
- `CACHE_TTL` (Redis): 300 секунд
- `LOCK_TTL` (Redis): 5 секунд
- Время ответа из Redis: 1–2 миллисекунды
- Задержка polling fallback: ≤ 60 секунд
- Попытки реконнекта Socket.IO: до 5 с экспоненциальной задержкой
