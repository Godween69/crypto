# Поток данных: Market Data & Redis Caching

## Архитектура запроса

Система построена по принципу слоистого кэширования с обратной связью. Фронтенд запрашивает цены через React Query, бэкенд маршрутизирует запрос через четыре уровня хранения, а Redis выступает основным распределённым слоем с жёстким контролем свежести данных.

## Этап 1: Инициация на фронтенде

Хук `useMarketData` формирует детерминированный `queryKey` на основе отсортированного массива символов. React Query проверяет внутреннее состояние: если данные отсутствуют или помечены как устаревшие (`staleTime: 60_000`), отправляется GET-запрос к `/market`. Параметр `staleTime` ограничивает частоту сетевых вызовов до 1 раза в минуту.

## Этап 2: Резолвинг и проверка Redis

Бэкенд получает массив символов и передаёт его в `CoinResolverService`. Сервис проходит по каскаду: память процесса → Redis → PostgreSQL → внешний API. После получения CoinGecko IDs бэкенд сортирует их и формирует уникальный ключ кэша в формате `market:bitcoin,ethereum`. Далее выполняется проверка Redis на наличие готовых рыночных данных.

## Этап 3: Обработка кэш-промаха и защита от Stampede

Если ключ отсутствует, срабатывает механизм защиты от параллельных промахов. Бэкенд пытается захватить распределённый лок через атомарную команду `SET key value EX ttl NX` с TTL 5 секунд. Если лок уже занят другим воркером, текущий поток переходит в режим ожидания 200 миллисекунд и повторно проверяет Redis. Это предотвращает синхронный наплыв 100 тысяч запросов на внешний API при истечении TTL.

## Этап 4: Внешний запрос и запись в кэш

Владелец лока выполняет единственный запрос к CoinGecko `/coins/markets`. Ответ нормализуется, приводится к внутреннему DTO и записывается в Redis с TTL ровно 300 секунд.

## Этап 5: Возврат данных

Фронтенд получает массив `MarketData[]`. React Query кэширует ответ в памяти браузера. При следующем взаимодействии пользователя или фокусе окна React Query проверяет `staleTime`, отправляет запрос, а бэкенд возвращает данные из Redis до истечения TTL. Цикл замыкается.

## Итог

Данные движутся по модели запрос-ответ: браузер → бэкенд → Redis → внешний API → Redis → браузер. При высоких нагрузках Redis абсорбирует ~99% запросов. Механизм локов гарантирует, что при истечении пяти минут обновлением займётся ровно один воркер, остальные получат готовые данные без нагрузки на инфраструктуру. Контракт данных минималистичен: фронтенд получает только массив цен, вся логика кэширования инкапсулирована на бэкенде.
